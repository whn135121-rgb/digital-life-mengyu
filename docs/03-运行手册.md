## 3. 人格与模型

- 生效人格：`cmd_config.json` → `agent_runner.config.persona.persona_id = "梦屿"`（personas 表 id=7，约 2101 字，含 `# 说说` 段与 anysearch 使用规则）。
- 内置人格 `default`（id=1，1708 字）**不要动**，它是 AstrBot 自带的；用户只管「梦屿」这一份。
- 梦屿人格结构：`# 角色 / # 气质 / # 说话方式 / # 关系和距离 / # 私聊和群聊 / # 认真的时候 / # 事实和工具 / # 说说 / # 记忆 / # 边界 / # 示例`。
- 模型：`deepseek_source/deepseek-flash`（`https://api.deepseek.com/v1`），fallback 同源，`request_max_retries=5`。
- Embedding：`siliconflow_embedding` = `BAAI/bge-m3`（1024 维），只给长期记忆用。
- 上下文压缩：`max_turns = -1`（按轮截断会让 `keep_recent_ratio` 失效，所以关掉）、`overflow_strategy = llm_compress`、`keep_recent_ratio = 0.25`、`fallback_max_tokens = 128000`。`deepseek-flash` 的 `max_context_tokens = 1048576`，压缩阈值约 86 万 token，正常聊天很难触发；触发后保留最近 25% token 原文，其余交给 LLM 摘要，摘要失败才退化为丢最旧轮次。
- 关掉按轮截断后，每轮输入随轮数增长（实测 50 条消息时约 1.1–1.2 万 token/轮、每轮 +200），到 86 万才触发压缩；想省 token 就把 `max_turns` 设回有限值。
- `misc.max_steps = 128`、`tool_call_timeout = 120`、`tool_schema_mode = full`。
- **工具清单**（2026-10-27 13:26 实测 `GET /api/v1/tools` 有 55 个注册项）：真正在用的插件工具 8 个 —— `search_memes`、`query_token_usage`、`recall_long_term_memory`、`life_state` / `life_update`、`anysearch_search` / `anysearch_extract` / `anysearch_batch_search`；内置侧另有 `send_message_to_user`、`get_group_message_history`、`future_task`、`astr_kb_search` 等常驻工具。
- **注入规则**：梦屿的 `personas.tools` 是 `null` → AstrBot 按「全部 active 工具」注入（`qqbot\AstrBot\astrbot\core\astr_main_agent.py:655-659`）。要给她做减法，得在人格里填 `tools` 白名单，而不是关插件。
- **安全边界**：`computer_use_runtime = "none"` 时不构建 runtime 计算机工具（shell / Python / 文件 / 浏览器走 runtime 通道，`astr_agent_tool_exec.py:302` 只加已存在的 runtime 工具），所以这些没进她的请求；但 skill 提示里仍会写一句「不能用 shell/Python」。
- **额度可自查**：`astrbot_plugin_token_usage` 注册了 `query_token_usage` 工具，她能在对话里回答「余额还剩多少 / 今天花了多少 token」。余额走 DeepSeek 官方 `GET https://api.deepseek.com/user/balance`，Key 由插件自动从 `provider_sources.deepseek_source.key` 读取（`auto_detect_key=true`，只允许官方域名）；`balance_admin_only=true` → 只有管理员（`admins_id` 里的号）能问出余额，其他人只能问 token 用量。实测 2026-10-26 13:24 工具返回「人民币 ¥35.85，可正常调用」。

## 11. 环境坑（踩过的，别再踩）

- 工作区根目录可写，**`qqbot\` 整个子树被沙箱拒写**（`VERDICT=NOT_THIS_CLASS`，不是 ACL 问题）→ 需要 `sandbox_permissions: danger-full-access` 逐次放行。
- 本机是 **PowerShell 5.1**，`Set-Content -Encoding UTF8` 会写 BOM → 写 JSON 一律用 python `write_text(encoding="utf-8")`；读带 BOM 的 JSON 用 `encoding="utf-8-sig"`（`cmd_config.json` 就是带 BOM 的）。
- `Get-NetTCPConnection` 在本会话不可靠（对在听的端口也返回空/False）→ 判断端口用 `netstat -ano | Select-String ':<port> .*LISTENING'`。
- `Start-Process` 起的后台进程会随本次 pwsh 调用结束被杀 → 常驻进程用 `run_in_background`。
- AstrBot 每次重启都会**清空** `qqbot\logs\astrbot.out.log`（`Start-Process -RedirectStandardOutput` 截断）。
- 控制台用 GBK 读 UTF-8 输出会乱码 → 读文件用 read 工具或 `-Encoding UTF8`。
- **git 推 GitHub 的两道坎（2026-10-27 实测）**：①TLS 层报 `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS` —— 系统 `http.sslbackend=schannel`，仓库级设 `http.sslBackend=openssl` 即通；②认证层这台机器**没有任何 credential helper**（无 GCM / 无 wincred），所以改用 SSH 密钥；③git 起 ssh 子进程要建管道，工作区写入模式拒（`couldn't create signal pipe, Win32 error 5`），推送命令要在 `danger-full-access` 下跑；④`ssh -i` 解析不了含空格的路径（工作区叫 `workspace`），脚本先把私钥复制到 `%LOCALAPPDATA%\Temp\dsh_gh\`。统一入口 `scripts\push-github.cmd`。
- **PowerShell 脚本被执行策略拦**（`.ps1` 无法加载）→ 用 `powershell -NoProfile -ExecutionPolicy Bypass -File xxx.ps1`，或走 `scripts\*.cmd` 包装器。
- **PS 5.1 读无 BOM 的 UTF-8 .ps1 会把中文注释读坏**，报出「Try statement is missing its Catch or Finally」这类假语法错 → 脚本正文用英文注释，中文只写在 .md 里。
- `tasklist` / `Get-Process -Id <别人的PID>` 在沙箱里受限，看不到全部进程。
- 插件热重载**不会**触发 `on_astrbot_loaded`，需要循环的插件要在 `initialize()` 里自己起。
- self_learning 的「注入」有两个开关，但只有一个是总线：`Runtime_Internal_Settings.enable_llm_hooks` 关着时，`Social_Context_Settings.enable_social_context_injection=true` 也不会有任何效果（`llm_hook_handler.py:109` 先 return）。改之前先确认总线。
- 在**工作区根目录**直接 `import astrbot`（比如为了读 schema）会按 CWD 生成一份 `data\`，里面是默认配置（`admins=astrbot`、人格 `default`、分段阈值 150）。**活配置只有 `qqbot\data\cmd_config.json`**，别改错文件、也别把根目录那份当备份。
- 限制她能用哪些工具：改 `personas` 表的 `tools` 字段（JSON 数组）。现在是 `null` = 「全部 active 工具」，所以任何新装的插件都会自动出现在她手里。
- **`plugin_data` 有两个**：活的是 `qqbot\data\plugin_data\`（livingmemory、proactive_chat、meme_manager、token_usage、qzone 留言），但 `astrbot_plugin_self_learning` 落在 `qqbot\AstrBot\data\plugin_data\`（它按 CWD 解析路径）。找它的库别在 `qqbot\data` 下翻。
- 读 `qqbot\AstrBot\data\...\messages.db` 会报 `unable to open database file`：因为 `qqbot\` 子树对沙箱只读，SQLite 建不了 `-shm`。用 `sqlite3.connect(f"file:{path}?immutable=1", uri=True)` 只读打开。
- **要写入这个库，普通 `workspace-write` 也不行**（`sqlite3.OperationalError: unable to open database file`，目录上有 `Everyone Deny DeleteSubdirectoriesAndFiles` 的沙箱 ACE），必须 `sandbox_permissions: danger-full-access`。库是 `journal_mode=delete`，写前先 `copy2` 备份到工作区；AstrBot 本身在跑，用 `BEGIN IMMEDIATE` + `busy_timeout` 拿锁。
- 市场安装不能传 `proxy`：`zip_updater.py:254` 会把代理拼到 URL 前面 → 400。

## 13. 常见问题

**适配器未连接**：确认 5099/6185/6199 在听；SnowLuma 日志应有 `[astrbot] connected ws://127.0.0.1:6199/ws`，AstrBot 日志应有 `aiocqhttp(OneBot v11) 适配器已连接。`

**SnowLuma 注入失败**：QQ 与 SnowLuma 必须同一用户、同权限启动；覆盖升级后重跑
`icacls "C:\path\to\workspace\qqbot\SnowLuma\node.exe" /setintegritylevel Medium`；QQ 大版本更新可能等 SnowLuma 适配。

**面板打不开**：先 `Ctrl+F5`，用 `http://127.0.0.1:6185` 别用 `localhost`；再看 `netstat` 有没有 6185，没有就手动跑 `start-all.ps1`；再看 `logs\astrbot.err.log` 与 `launcher.log` 末尾。

**忘记密码**：见 `qqbot\config\credentials.txt`；SnowLuma 可删 `SnowLuma\config\webui.json` 重新生成，AstrBot 可 `--reset-password`。

**端口冲突**：改 `SnowLuma\config\runtime.json` 的 `webuiPort`、`onebot.json`/`onebot_BOT_QQ.json` 端口，同步改 AstrBot 的 `ws_reverse_port` 与 SnowLuma `wsClients.url`。

## 14. 安全

- 所有服务绑定 `127.0.0.1`，不要改成 `0.0.0.0` 暴露公网——这些端口可以完全控制你的 QQ。
- `qqbot\config\onebot-token.txt`、`credentials.txt`、`cmd_config.json` 里的 API Key 都不要外发。
- 第三方 QQ 协议端有风控风险，遵守 QQ 用户协议，建议用小号。
- 人格/记忆里会有真实聊天内容（`data_v4.db`、`livingmemory.db`、`SnowLuma\...\messages.db`），分享日志前先脱敏。

三个判据全绿之前，这条大方向就还没成立；任何新功能都不该插到它们前面。

### 16.3 分支详情

#### S1 状态内核：从「作息表」到「有想要的状态机」

**为什么**：现在她知道自己「正在上课」，但不知道自己「想不想说话」。`life_state.py` 是纯函数按时间查表，没有任何可累积的东西——所以她永远是被动应答。

**现状**：`qqbot\data\life\life_state.py`（18 段作息）+ `qqbot\data\life\state.json`（`fact.schedule` 快照 + `self` 四字段 + `drives` 四驱力 + `decision` 判断 + 推进记账），由 `astrbot_plugin_life` v0.3.2 独占写并注入；**四驱力、阈值判断、判断的消费方（sleepy 不发 / opener 提前）都已落地**，仍缺 `recognition` / `achievement`（要关系与成就数据）与「拒绝」出口。

**交付物**
- [x] `life/state.json` 落地：`fact`（时间/时段/地点/在做什么/感觉/细节/跨分钟刷新）+ `self`（activity/location/mood/note，`null` = 未设置）+ `drives`（social/curiosity/play/rest）+ `decision`（action/reason/value/at）+ 推进记账
- [x] 每小时推进任务（幂等键 `(date, hour)`，重复执行不叠加）
- [x] 四驱力一阶滤波：`v_t = 0.7·v_{t-1} + 0.3·v_target`，`v_target` 由作息段 + 空闲分钟数决定（`social = min(0.95, 0.15 + 闲置/75)`，上课压 0.72、睡觉压 0.20、静默压 0.25）
- [x] 阈值 → 判断映射：`social ≥ 0.7` 且闲置 ≥ 45 分钟 → `opener`（写进 `state.json`，并让注入多一句「你隔了一阵没人说话，这会儿正想找他」）；**只判断不发送**，发送仍归 proactive_chat
- [x] 注入改由 life 插件自己做：读 `state.json` 的 `fact.schedule`（作息快照）+ 她自填的 `self`；`ai_delay` 的旧 `inject_life_state()` 留成兜底开关（默认关）
- [x] `sleepy` 判断接进主动消息：`proactive_chat\core\chat_flow.py` 的 `_is_chat_allowed()` 读 `state.json`，睡着就不发（读不到 fail-open）；主动消息的状态行也换成读 `state.json` 的版本
- [x] 把 `opener` 提前：`social ≥ 阈值` 时不等 20–180 分钟的倒计时——`proactive_chat\core\task_scheduler.py` 的 `_opener_pullin_loop()` 每 120 秒读一次 `state.json`，`opener` 时用 `_add_chat_job()` 把下一次改到 1–4 分钟后（冷却 30 分钟，免打扰/未回复上限/临近排期都不动）；只改时间，发不发仍由 `_is_chat_allowed()` 决定

#### S2 调度地基：单 scheduler + 持久化任务 + 心跳

**为什么**：概念文档 §7.1 的强制约束。现在七条任务分属各插件的 `asyncio` 循环和 APScheduler，热重载不触发 `on_astrbot_loaded`，重启后静默归零——这是整套「自主节律」最脆的一环。

**现状**：proactive_chat（APScheduler）、livingmemory（asyncio 常驻，00:05 衰减）、self_learning（采集/衰减）、meme/token 按需调用，`life` 另有 30 秒推进 + 60 秒心跳；**调度层没有统一 jobstore、没有启动自检**，各插件各管各的循环。

**交付物**
- [ ] 单一 scheduler 进程（APScheduler + `SQLAlchemyJobStore` 落 `life/jobs.db`），独立于插件热重载
- [ ] 现有任务登记进去：生命状态推进、主动消息、记忆衰减、token 记账、情绪推进、周报
- [ ] `life/heartbeat.json` 每 60 秒更新（`{ts, loop, jobs: N, last_job}`）
- [ ] 启动自检：任务数 < 期望 或 心跳超 3 分钟 → 日志 ERROR + 自动重建 + 告警日志
- [ ] 任务失败重试上限 3 次，超限标红并跳过，不阻塞后续
- [ ] **会话交接**（v4 §7.6）：按成功回复计数，满 25 轮把最近消息压成 3 句写 `life/handover.json`，新会话开头注入（单次约 95 token）；与 `llm_compress` 分工不同——它防溢出，交接防「换会话就失忆」
- [ ] **消息补漏**（v4 §7.6）：重连时若掉线 > 1.5 分钟，拉最近 30 条私聊写入交接备忘并归档，**不自动回复**；> 24 小时不补
- [ ] **参数版本化**（v4 §10.3）：`life/params.json` 分四类（结构常量 / 自动调参 / 漂移量 / 行为参数），带 version，改前快照、可回滚；现在行为参数散在各插件 config 里，无版本无回滚
- [ ] **看护唯一性**：确认 `start-all.ps1` 是唯一看护，插件内不再新增重启逻辑（v4 踩过三个看护互相重启、登录态反复失效）

**验收**
- 杀掉进程再起：2 分钟内 `jobs` 数恢复，`heartbeat.json` 的 `ts` 在走

### 16.4 顺序与依赖

第一步不是 scheduler，而是三件互不依赖的小事，各约半天：**S1 去结论化**、**S2 会话交接 + 消息补漏**、**S2 参数版本化**。它们都不动调度、都能单独验收，做完再动 scheduler，风险最小。

```
S2 调度地基 ──┬─→ S1 状态内核 ──┐
              │                  ├─→ S5 世界（要状态与定时器都稳）
              └─→ S3 记忆取舍 ───┘
S4 关系可见 ──（随时插入，1–2 天，不依赖别人）
```

- **S1 与 S2 必须同批设计**：状态机没有定时器推不动，而现在的任务撑不住这个职责。
- **S3 排在 S5 前**：世界产物要进上下文，先得有个预算，否则提示词继续膨胀。
- **S4 随时可做**：改动最小、可回滚、对判据无副作用。
- **S3 的检索侧只做标定**：分舱、证据链、边类型先出报告（候选集大小 + 3 个真实问题的召回对比），达标才写进线上；不达标就留在文档里当参考实现。
